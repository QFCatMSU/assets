Adding GitHub Team Authentication to a Website on the QFC Server

0.1 To-do

  • A better way to pick port numbers?
  • Better way to structure the Nginx file? Does it have to be one file?

1 Overview

This procedure adds GitHub Team authentication to an already deployed static website or Shiny application on https://qfc.msu.edu. The GitHub Teams are created in the QFC-auth organization.

 

Prerequisites:

  • Ubuntu Server with Nginx (HTTPS), OAuth2 Proxy, and systemd installed.

  • sudo access to the server

  • a deployed website or shiny app

  • write access to the QFC-auth GitHub organization

 

These examples use micro to edit server configuration files. All text for the configuration files in this document assume the website is named biology and the port number is 4183. The example values, biology and 4183, need to be changed throughout.

1.1 Server files added or modified

For each new protected website, two files are added to the server and one file is modified:

Added: /etc/oauth2-proxy/oauth2-proxy-biology.cfg

  • OAuth provider, GitHub organization/team, app credentials, callback, cookie, and unique local port.

Added: /etc/systemd/system/oauth2-proxy-biology.service

  • Runs and restarts the site-specific OAuth2 Proxy instance.

Modified: /etc/nginx/sites-available/default

  • Adds protected site routing, sign-in redirect, OAuth2 endpoints, and auth check within the HTTPS server block.

2 Create a GitHub team

In GitHub, open https://github.com/orgs/QFC-auth/teams and create a new team named biology.

2.1 Adding members

Members can be added and removed on GitHub at any time. The first time a member is added to the organization, that member will receive an invite to the QFC-auth organization. They will have to accept the invite before they can be authorized.

3 Create a GitHub OAuth application

In the QFC-auth organization go to: Settings -> Developer Settings -> Oauth Apps -> new Oauth app and use the following values:

  • Application name: QFC Biology

  • Homepage URL: https://qfc.msu.edu/biology/

  • Description: Authentication for Biology

  • Authorization callback URL: https://qfc.msu.edu/oauth2-biology/callback

 

Record the new Client ID and generate a new Client Secret – you will use these two values in Section 4.3 . Never share the secret value.

4 Create the OAuth2 Proxy configuration

Each website requires its own OAuth2 Proxy configuration file. We will create a new file using biology as the example website.

4.1 Select an available port <find a better way to pick a port #?>

OAuth2 Proxy instances needs a unique port. We started with 4180.

 

This command finds the first candidate port, starting at 4180, that is not currently listening and is not assigned to an existing OAuth2 Proxy configuration:

for port in $(seq 4180 65535); do
    if ! ss -H -ltn "sport = :$port" | grep -q . &&
       ! sudo grep -RqE "http_address\s*=.*:$port([\"[:space:]]|$)" /etc/oauth2-proxy/; then
        echo "Available port: $port"
        break
    fi
done

Use the Available port number given after running this command. For these instructions, we will assume the port number is 4183.

4.2 Generate a cookie secret

Each OAuth2 Proxy instance should have its own cookie secret. Run the following:

openssl rand -base64 32 | tr '+/' '-_' | tr -d '\n'

Copy the generated value. You will use it for cookie_secret in the configuration below.

4.3 Create the configuration file

The first command creates the new configuration file with root access (if the file does not exist already). The second command opens the file in micro:

sudo sh -c 'umask 077; set -C; : > /etc/oauth2-proxy/oauth2-proxy-«biology».cfg'
sudo micro /etc/oauth2-proxy/oauth2-proxy-«biology».cfg

Copy and paste the text below into the new file. Replace the highlighted values in the text below with:

  • biology — Your GitHub team slug

  • YOUR_CLIENT_ID — Client ID from Section 3

  • YOUR_CLIENT_SECRET — Client Secret from Section 3

  • YOUR_GENERATED_COOKIE_SECRET — Value generated in section Section 4.2

  • 4183 — The port number found in Section 4.1

provider = "github" 

github_org = "QFC-auth" 
github_team = "«biology»" 

client_id = "«YOUR_CLIENT_ID»" 
client_secret = "«YOUR_CLIENT_SECRET»" 

redirect_url = "https://qfc.msu.edu/oauth2-«biology»/callback" 

cookie_name = "_oauth2_proxy_«biology»" 
proxy_prefix = "/oauth2-«biology»" 

http_address = "127.0.0.1:«4183»" 

cookie_secret = "«YOUR_GENERATED_COOKIE_SECRET»" 
cookie_secure = true 
cookie_httponly = true 

email_domains = ["*"] 
whitelist_domains = ["qfc.msu.edu"] 
reverse_proxy = true 
trusted_proxy_ips = ["127.0.0.1/32", "::1/128"]

5 Create and start the systemd service

Each website requires its own systemd service to run OAuth2 Proxy. We will create a new service using biology as the example website.

5.1 Create the service file

Open a new file using micro:

sudo micro /etc/systemd/system/oauth2-proxy-«biology».service

Replace biology in the text below with your website name, paste the text to the file, and save:

[Unit]
Description=OAuth2 Proxy - «Biology»
After=network-online.target
Wants=network-online.target
 
[Service]
Type=simple
ExecStart=/usr/local/bin/oauth2-proxy --config=/etc/oauth2-proxy/oauth2-proxy-«biology».cfg
Restart=on-failure
RestartSec=5
 
[Install]
WantedBy=multi-user.target

5.2 Reload systemd

Notify systemd that a new service has been created:

sudo systemctl daemon-reload

5.3 Enable and start the service

Enable the service to start automatically when the server boots, and start it immediately:

sudo systemctl enable --now oauth2-proxy-«biology»

5.4 Verify the service is running

Check the service status:

sudo systemctl status oauth2-proxy-«biology» --no-pager

The output should include:

Active: active (running)

Confirm the service is active before continuing.

6 Configure Nginx

Nginx controls how visitors access websites on the QFC server. Nginx is configured to:

  1. Identify websites that require authentication.

  2. Check whether a visitor is authorized through OAuth2 Proxy.

  3. Redirect unauthorized visitors to GitHub authentication.

  4. Serve the website after successful authentication.

 

Nginx configuration differs between static websites (e.g., Quarto websites) and Shiny applications – both examples are given.

6.1 Backup the Nginx configuration file

The Nginx file is vital and should be backed up before you edit it. This command will create a backup in the same folder with a time stamp in the name:

sudo cp /etc/nginx/sites-available/default \
  "/etc/nginx/sites-available/default.bak.$(date +%Y%m%d-%H%M%S)"

6.2 Open the Nginx configuration file

sudo micro /etc/nginx/sites-available/default

The file contains two server blocks:

  • The first, and far smaller, redirects HTTP requests to HTTPS.

  • The second handles HTTPS requests and contains the website configurations.

 

All new configuration needs to be added inside the second server block, before the final location / block that redirects unmatched requests to the main QFC website.

 

For each new website, we will add a section containing the website configuration and its authentication endpoints.

6.3 Configure the protected website

Choose one of the following configurations, depending on the type of website.

6.3.1 Static website (e.g., Quarto, HTML)

Use this configuration for a static website whose HTML files are stored on the server.

 

For this example, we assume:

  • Website URL: https://qfc.msu.edu/biology/

  • Website directory: /var/www/html/biology/docs/ (Quarto pages typically use docs as the host folder)

  • OAuth2 Proxy prefix: /oauth2-biology

 
Add the following configuration (replace biology with the website):

# ======================================================== 
# «BIOLOGY» — PROTECTED STATIC WEBSITE 
# ======================================================== 
# GitHub organization: QFC-auth 
# GitHub team: «biology» 
# Website directory: /var/www/html/«biology»/docs/ 
# ======================================================== 

location /«biology»/ { 
    auth_request /oauth2-«biology»/auth; 
    error_page 401 = @oauth2_«biology»_signin; 
    
    alias /var/www/html/«biology»/docs/; 
    index index.html; 
} 

# Redirect /«biology» to /«biology»/ 
location = /«biology» { 
    return 301 /«biology»/; 
}

How this works:

  • location /biology/ identifies the website being protected.

  • auth_request asks OAuth2 Proxy whether the visitor is authorized.

  • error_page 401 redirects unauthorized visitors to the sign-in process.

  • alias identifies the directory containing the website files.

  • index index.html specifies the default page.

  • The second location block ensures that /biology redirects to /biology/.

 

Important: The alias path must match the actual location of the website files. For a Quarto website, this will typically be the docs directory.

6.3.2 Shiny application

Use this configuration for an application running through Shiny Server.

 

For this example, we assume:

  • Application URL: https://qfc.msu.edu/biology/

  • Shiny Server: port 3838

  • Shiny application path: /biology/

  • OAuth2 Proxy prefix: /oauth2-biology

 

Add the following configuration (replace biology with the website):

# ======================================================== 
# «BIOLOGY» — PROTECTED SHINY APPLICATION 
# ======================================================== 
# GitHub organization: QFC-auth 
# GitHub team: «biology» 
# Shiny Server: 127.0.0.1:3838 
# ======================================================== 
location /«biology»/ { 
    auth_request /oauth2-«biology»/auth; 
    error_page 401 = @oauth2_«biology»_signin; 
    
    proxy_pass http://127.0.0.1:3838/«biology»/; 
    proxy_http_version 1.1; 
    
    proxy_set_header Host $host; 
    proxy_set_header X-Real-IP $remote_addr; 
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; 
    proxy_set_header X-Forwarded-Proto $scheme; 
    
    # Required for Shiny WebSocket connections 
    proxy_set_header Upgrade $http_upgrade; 
    proxy_set_header Connection "upgrade"; 
} 
    
# Redirect /«biology» to /«biology»/ 
location = /«biology» { 
    return 301 /«biology»/; 
}

How this differs from a static website:

  • proxy_pass forwards requests to Shiny Server instead of serving HTML files directly.

  • proxy_http_version 1.1 enables HTTP/1.1 communication with Shiny Server.

  • The Upgrade and Connection headers support WebSocket connections, which Shiny uses for interactive communication.

  • The remaining proxy headers pass information about the original request to Shiny Server.

 

The Shiny application must already be deployed and accessible through Shiny Server.

6.4 Configure the authentication endpoints

This section is for both static websites and Shiny applications.

 

Add the following blocks after the website configuration. Thise blocks connect Nginx to the OAuth2 Proxy instance created in Section 4.3 and Section 5.1 .

# ======================================================== 
# «BIOLOGY» — GITHUB AUTHENTICATION 
# ======================================================== 
# OAuth2 Proxy service: oauth2-proxy-«biology» 
# OAuth2 Proxy port: «4183»
# OAuth2 Proxy prefix: /oauth2-«biology» 
# ======================================================== 
# Redirect unauthenticated visitors to sign-in 
location @oauth2_«biology»_signin { 
    return 302 /oauth2-«biology»/sign_in?rd=$scheme://$host$request_uri; 
} 

# Forward OAuth2 requests to OAuth2 Proxy 
location /oauth2-«biology»/ { 
    proxy_pass http://127.0.0.1:«4183»; 
    
    proxy_set_header Host $host; 
    proxy_set_header X-Real-IP $remote_addr; 
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; 
    proxy_set_header X-Forwarded-Proto $scheme; 
} 

# Check whether visitors are authenticated 
location = /oauth2-«biology»/auth { 
    internal; 
    
    proxy_pass http://127.0.0.1:«4183»/oauth2-«biology»/auth; 
    
    proxy_pass_request_body off; 
    proxy_set_header Content-Length ""; 
    
    proxy_set_header X-Original-URI $request_uri; 
    proxy_set_header X-Real-IP $remote_addr; 
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; 
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header Host $host; 
}

How these blocks work:

Sign-in redirect

  • The @oauth2_biology_signin block sends unauthorized visitors to the OAuth2 Proxy sign-in page.

  • The rd parameter records the original URL so users can return to the requested page after authentication.

 

OAuth2 Proxy endpoints

  • The /oauth2-biology/ block forwards authentication-related requests to the OAuth2 Proxy service running on port 4183.

  • These requests include the GitHub OAuth callback and authentication cookies.

 

Authentication check

  • The /oauth2-biology/auth block allows Nginx to ask OAuth2 Proxy whether the current visitor is authorized.

  • The internal directive prevents visitors from accessing this endpoint directly while allowing Nginx to use it for authorization checks.

6.5 Save and test the configuration file

Check to make sure the new configuration is valid:

sudo nginx -t

If the configuration is valid, you should see:

nginx: the configuration file /etc/nginx/nginx.conf syntax is ok 
nginx: configuration file /etc/nginx/nginx.conf test is successful

If an error is reported, return to the configuration file and correct it before proceeding.

 

Do not proceed until the configuration test succeeds.

6.6 Reload nginx

Reload Nginx to apply the changes without stopping the server:

sudo systemctl reload nginx

The new website should now require GitHub authentication.

6.7 Verify the website

Open a private browser window and visit: https://qfc.msu.edu/biology/

  • You should be redirected to GitHub authentication

  • After signing in, users belonging to the appropriate GitHub team should be able to access the website.

  • Users who are not members of the team should be denied access.

6.8 Troubleshooting

For troubleshooting:

sudo journalctl -u oauth2-proxy-«biology» -n 50 --no-pager

7 Manage access in GitHub

To grant or revoke access, add or remove users from the biology team in QFC-auth. No changes to server configuration files are required.
